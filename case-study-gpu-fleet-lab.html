Systems engineering case study

GPU Fleet Lab

A GPU resource health, scheduling, and capacity control-plane prototype built to demonstrate how AI infrastructure can evaluate accelerator health, VRAM, utilization, topology, and recovery behavior before placing workloads.

PythonFastAPINVIDIA DCGMPrometheusGrafanaPostgreSQLDockerPytest

The problem

GPU-backed AI workloads cannot always be placed on the first available accelerator. A scheduler may need to consider device health, available VRAM, utilization, temperature, requested GPU count, and the communication topology between devices. If no valid placement exists, the safer behavior is to queue the job rather than violate its requirements.

What I built

  • FastAPI control plane with REST endpoints for fleet state, GPU state, jobs, topology, and recommendations.
  • Policy-based scheduler with human-readable decision explanations.
  • Multi-GPU placement with P2P/NVLink affinity checks.
  • TelemetryProvider abstraction supporting simulation telemetry and NVIDIA DCGM metric mapping.
  • Queue reconciliation after capacity or health recovers.
  • Prometheus-compatible metrics, Grafana configuration, PostgreSQL-ready job history, and automated tests.

Architecture

I separated the project into a control plane, fleet state, scheduler, telemetry provider, persistence layer, and observability layer. The telemetry abstraction keeps scheduling logic independent from the source of metrics: the same internal GPU model can be fed deterministic simulation data for repeatable demos or mapped from NVIDIA DCGM Exporter metrics in an environment with real NVIDIA accelerators.

Scheduling logic

The scheduler filters out unhealthy, quarantined, or undersized devices, evaluates requested GPU count and memory requirements, and checks topology requirements for multi-GPU workloads. Eligible placements are scored using factors such as idle capacity, available memory, thermal headroom, fit, and topology locality. The API returns a readable explanation of why a GPU or GPU group was selected.

Failure and recovery walkthrough

I tested the system as an incident rather than only as a happy-path demo. A two-GPU workload requiring P2P/NVLink locality was scheduled to the simulated H100 pair. I then injected an overheat fault into one H100, moving it to a degraded state at 96°C. New topology-constrained workloads stayed queued because the only valid pair was no longer fully healthy. After clearing the fault, the device returned to healthy status and the reconciliation loop automatically re-evaluated and started the waiting jobs.

Saturation investigation

A controlled capacity test placed multiple 40%-target workloads on the same H100 pair. The simulated GPUs reached 99% utilization and the findings engine raised Compute saturation risk warnings. That test exposed the next engineering milestone: projected-utilization admission control so the scheduler can prevent avoidable saturation before it occurs instead of only detecting it afterward.

What this demonstrates

GPU Fleet Lab demonstrates Python backend development, API design, systems thinking, resource scheduling, multi-GPU topology awareness, observability, fault injection, capacity management, automated testing, and iterative performance engineering.

Portfolio scope

The default demo uses simulated accelerator telemetry so it can run on a normal development computer. The scheduling logic, REST API, topology rules, queue behavior, decision explanations, findings engine, and tests are working software. The project should be read as a systems-engineering prototype, not as a claim of operating a production H100 cluster.
