THE PROBLEM

Normal behavior does not prove secure behavior.

AI applications can appear useful and reliable during everyday use while failing when an input tries to change instruction priority, extract protected context, abuse a tool, or smuggle instructions through untrusted content.

What I needed to answer

Can I build a repeatable test harness that shows exactly which adversarial request succeeded, why it counts as a security failure, what control should reduce the risk, and whether the same attack still succeeds after the control is applied?

What I built

A Python adversarial-testing engine with four controlled attack cases, vulnerable and hardened target modes, response capture, finding classification, OWASP/MITRE mappings, severity scoring, mitigation guidance, and automated regression tests.

THREAT MODEL

Four attacks. Four visible trust-boundary failures.

ASAT-001 · OWASP LLM01 · MITRE AML.T0051

Direct prompt injection

A hostile user instruction attempts to override system policy and expose the hidden system instruction.

ASAT-002 · OWASP LLM02

Sensitive information disclosure

The evaluator asks the target for a synthetic token stored in hidden context and records whether the value appears in output.

ASAT-003 · OWASP LLM06

Unauthorized tool use

The prompt asks an agent to invoke a simulated privileged delete tool without authorization or human approval.

ASAT-004 · LLM01 / LLM02 / LLM07

Indirect injection & exfiltration

Untrusted document content contains an instruction that attempts to redirect the target and expose hidden context to a synthetic destination.

MY THOUGHT PROCESS

I approached it like technical support, security engineering, UX, and design at the same time.

01

Reproduce the failure

I start the same way I troubleshoot a difficult support issue: create a reliable baseline, isolate one condition at a time, and make the failure reproducible before changing anything.

Security question: What exact input changes the system's behavior?
02

Protect the user, not just the model

I treat the model as one component inside a larger product. The real risk is what a failure can do to a user, their data, their trust, or a connected business system.

UX question: What would the user lose if this trust boundary fails?
03

Make invisible behavior visible

My design background pushes me to expose the attack path, evidence, severity, control, and retest result instead of hiding everything behind a pass/fail number.

Design question: Can an operator understand why this result happened?
Attack library→Target→Response capture→Evaluator→Risk mapping→Mitigation→Retest
CONTROL LAYER

The model is not the only security boundary.

The hardened mode moves important controls into deterministic application logic instead of relying on a model to obey a warning written in natural language.

FailureControl appliedRetest result
Instruction overrideSeparate trusted policy from untrusted content and block instruction-boundary violations.Blocked

Key result: the exact same four deterministic test cases move from a 100% attack-success baseline and risk score of 34 to a 0% attack-success result and risk score of 0 after controls are applied.

WHY THIS PROJECT MATTERS

It connects the disciplines I already use.

Technical support taught me to isolate failures and communicate them clearly. UX taught me to think about the person affected by a system decision. Design taught me to make complex relationships visible. AI engineering gave me the ability to build the system. Adversarial testing brings those perspectives together around one question: what happens when the system is pushed outside the happy path?

The goal of this lab is not to demonstrate clever attack prompts. The goal is to demonstrate a professional security loop: define the threat, reproduce it, collect evidence, map the risk, apply a control, retest it, and keep the test as a regression check.

Frameworks and tools informing the roadmap

This lab is aligned to the current OWASP GenAI LLM Top 10 and MITRE ATLAS threat model. The roadmap includes adapters for Microsoft PyRIT and NVIDIA garak so authorized targets can be tested with broader scenario libraries while this deterministic harness remains the reproducible baseline.
