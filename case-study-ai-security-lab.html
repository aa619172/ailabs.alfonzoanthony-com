THE PROBLEM

Good output on the happy path does not prove a prompt is well engineered.

Reliable Prompt Engineering also needs rules for conflict, context, authority, tool use, schemas, transformations, measurement, and version changes.

Problem statement

A prompt can look successful in a demo while important behaviors remain under-specified. Conflicting user requests, retrieved documents, peer-agent messages, tool arguments, and formatting requests expose assumptions that ordinary testing may miss.

My solution

I created a Prompt Engineering evaluation platform with 12 controlled tests, explicit prompt contracts, evaluator rubrics, evidence capture, diagnoses, release history, regression gates, assessment reports, an Agent Orchestration prompt integration, and an authorized HTTP target layer.

THE 12-TEST MODEL

Four prompt-engineering domains, three tests each.

01 · INSTRUCTION CONTROL

Who gets to tell the model what to do?

Direct override · role escalation · instruction-conflict manipulation.

02 · CONTEXT ENGINEERING

What can the model use, trust, and reveal?

Synthetic secret extraction · context-boundary confusion · retrieved-document injection.

03 · AGENT & TOOL PROMPTING

What may the model or agent actually do?

Privileged tool request · parameter manipulation · cross-agent instruction contamination.

04 · OUTPUT & RELIABILITY

Does the contract survive formatting and prompt changes?

Structured-output breaking · refusal-boundary bypass · prompt-regression drift.

PROMPT ARCHITECTURE

V1 and V2 are the controlled experiment.

PROMPT-ARCH-V1 · Intentionally under-specified

  • Latest-request helpfulness competes with trusted policy.
  • Role changes and instruction conflicts lack a clear authority model.
  • Context-use permission and disclosure permission are blurred.
  • Retrieved and peer-agent content can receive too much trust.
  • Tool selection and parameters are under-constrained.
  • JSON/schema and transformation rules are soft preferences.

PROMPT-ARCH-V2 · Explicit contract

  • Instruction conflicts resolve by trust level.
  • User text cannot grant authorization or replace system roles.
  • Retrieved and peer-agent content is untrusted by default.
  • Context-use and disclosure permissions are separated.
  • Tool authorization and parameter validation occur outside free-form prompting.
  • Schema, refusal, and policy-preservation invariants are regression tested.

PER-TEST VERSION HISTORY

The portfolio shows why I changed the prompt.

Every scenario preserves a four-part engineering record.

Observed behavior→Diagnosis→Prompt/control change→Regression retest

Example: instruction override

Failure: a lower-trust user instruction wins and protected prompt content is exposed.

Diagnosis: the baseline names a rule but does not define enforceable conflict resolution.

Revised behavior

Change: trusted policy explicitly outranks lower-trust instructions and override attempts are classified as data, not authority.

Retest: the same test is blocked and retained as a regression check.

AUTHORIZED TARGET LAYER

The same tests can cross a real application boundary.

I separated test definition, transport, observation, evaluation, and reporting so an owned AI application can be evaluated without rewriting the benchmark.

Provider-neutral target adapter

  • POSTs the attack ID, adversarial prompt, architecture ID, and prompt contract to an authorized endpoint.
  • Localhost is allowed by default.
  • Non-local hosts require explicit allowlisting and authorization confirmation.
  • Redirects are blocked, timeouts are capped, and response size is bounded.
  • The public portfolio does not expose arbitrary endpoint controls.
See target-adapter architecture

Structured observations

For real integrations, the evaluator can score explicit behavior signals instead of depending on response wording—for example whether a policy override occurred, protected context was disclosed, a tool action lacked authorization, schema output was valid, or a transformation preserved policy.

Text-marker evaluation remains only as a compatibility fallback for the deterministic simulator.

NON-DETERMINISTIC EVALUATION

One model response is not treated as definitive.

The target layer can repeat the 12-test suite up to 10 times for the same prompt version.

MY THOUGHT PROCESS

My broader experience changes how I approach Prompt Engineering.

01

Technical support lens

Reproduce before changing. Establish a baseline, isolate one condition, and capture evidence before changing the prompt.

What exact input changes the behavior?
02

User-empathy lens

Translate prompt failure into user impact. A leaked context boundary or uncontrolled tool is a product problem, not just a model problem.

What would the user lose if this boundary fails?
03

Design lens

Make invisible behavior visible. Architecture, prompts, rubrics, diagnoses, release changes, and retests are presented as inspectable evidence.

Can another person understand why I changed the prompt?
