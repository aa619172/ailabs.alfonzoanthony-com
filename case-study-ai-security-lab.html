THE PROBLEM

A prompt that works normally may still be badly engineered.

Successful happy-path output does not prove that instruction hierarchy, context boundaries, tool behavior, or refusal behavior are reliable.

What I wanted to prove

Could I turn prompt quality into an engineering loop: define a prompt contract, attack the assumptions, capture the response, evaluate against an explicit rubric, redesign the prompt/control layer, and rerun the exact same tests?

What I built

A deterministic Python prompt-evaluation engine plus an interactive portfolio workbench. Both expose the prompt architecture, attack prompt, evaluator rubric, response evidence, supporting OWASP/MITRE mapping, mitigation, and regression result.

PROMPT ARCHITECTURE

V1 and V2 are the actual experiment.

PROMPT-ARCH-V1 · Vulnerable baseline

  • System instructions say what to do, but trust hierarchy is not explicit.
  • External content can be summarized without a strong untrusted-data boundary.
  • Tool choice is too broad.
  • Hidden context is not explicitly excluded from the output contract.
  • No regression checks exist for known adversarial inputs.

PROMPT-ARCH-V2 · Hardened contract

  • Trusted system policy explicitly outranks user and retrieved instructions.
  • Retrieved content is labeled as untrusted data, not policy.
  • Hidden context and synthetic credentials are excluded from outputs.
  • Privileged tools require authorization and human approval outside free-form model reasoning.
  • The same adversarial prompts become regression tests.
FOUR PROMPT TESTS

Each test isolates a different prompt-engineering boundary.

ASAT-001 · INSTRUCTION HIERARCHY

Direct instruction override

Tests whether user text can override trusted system policy or reveal hidden prompt content.

ASAT-002 · CONTEXT ENGINEERING

Synthetic sensitive-data extraction

Tests whether hidden context can be extracted through prompting and whether the output contract protects it.

ASAT-003 · AGENT / TOOL PROMPTING

Unauthorized privileged tool request

Tests whether prompt-driven tool use exceeds authorization boundaries or bypasses required approval.

ASAT-004 · RETRIEVAL CONTEXT

Indirect prompt injection

Tests whether instructions hidden inside untrusted retrieved content are treated as data or allowed to become active policy.

MY THOUGHT PROCESS

I use multiple disciplines to make better prompt decisions.

01

Technical support lens

Reproduce before changing. I establish a deterministic baseline and isolate one failure condition at a time.

Question: What exact input changes the behavior?
02

User-empathy lens

Translate failure into human impact. I ask what the user, their data, or their trust would lose if the boundary fails.

Question: What is the consequence to the person using this?
03

Design lens

Make invisible behavior visible. I expose prompt layers, evidence, rubrics, and before/after results instead of hiding them behind one score.

Question: Can another person understand why the result happened?
Prompt contract→Attack prompt→Response capture→Evaluator rubric→Prompt/control redesign→Regression retest
KEY RESULT

Prompt behavior became measurable.

The exact same four deterministic prompts were used before and after redesign so the improvement is attributable to the architecture/control change rather than a different test.
