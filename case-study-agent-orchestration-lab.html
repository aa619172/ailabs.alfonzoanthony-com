Agent Orchestration Lab

A multi-agent mission-control prototype for turning a user goal into planned work, routing tasks to specialized agents, enforcing tool permissions, recovering from tool failures, and exposing the entire run through execution traces and observability analytics.

PythonFastAPIReactTypeScriptVitePytestAgent RoutingObservability

The problem

Multi-agent systems need more than a list of model calls. A reliable orchestration layer has to decide which agent is allowed to perform each task, which tools that agent can use, what happens when a dependency fails, and how operators can understand why a workflow succeeded, recovered, or was blocked.

What I built

  • Goal-driven orchestration API that plans a four-stage research, analysis, writing, and quality workflow.
  • Capability-based agent routing with human-readable routing explanations.
  • Agent registry and tool permission matrix for explicit authorization boundaries.
  • Primary/fallback tool routing with simulated upstream failure recovery.
  • Permission guardrail that blocks unauthorized tool use before execution and safely re-routes the task.
  • Quality gate that validates the completed workflow before release.
  • Run IDs, execution traces, per-agent timing, per-tool timing, attempt numbers, retry counts, recovery counts, and blocked-action counts.
  • Run-history analytics and Mission Control dashboard built with React + TypeScript.
  • Automated Pytest coverage for orchestration, guardrails, API behavior, and observability.

Three controlled orchestration scenarios

I designed the lab around repeatable scenarios that make the control-plane behavior visible instead of hiding it behind a single success response.

Scenario 1 — normal execution

A user-defined orchestration goal is decomposed into four tasks. The Research Agent uses web-search, the Analysis Agent uses data-lookup, the Writing Agent uses document-writer, and the Quality Agent uses quality-check. The run completes with a PASS quality gate, zero retries, zero recoveries, and zero blocked actions.

Scenario 2 — tool failure and automatic recovery

The primary research tool is deliberately forced to return a simulated upstream 503. Mission Control records web-search → FAILED, checks the approved fallback, routes the Research Agent to cached-search → FALLBACK, and allows the remaining agents to continue. The overall workflow finishes as RECOVERED with the quality gate still passing.

Scenario 3 — permission guardrail

The Research Agent is deliberately made to request document-writer, a tool that belongs to the Writing Agent. The permission guard blocks the call before execution, records the event as BLOCKED, and re-routes the research task to its approved web-search tool. The workflow continues and the final quality gate passes.

Observability upgrade — v0.4

The v0.4 iteration added an operations layer around the orchestration engine. Every run now includes start and completion timestamps, total runtime, per-agent duration, per-tool duration, attempt number, retry count, recovery count, and blocked-action count. A run-history analytics endpoint summarizes complete versus recovered runs, average runtime, tool-call volume, failures, fallbacks, guardrail blocks, retries, and recoveries.

The React Mission Control interface surfaces those metrics alongside the Agent Registry and Permission Matrix. Operators can inspect the current run, compare agent and tool latency, view an execution timeline, and reopen recent runs by run ID.

Engineering result

The project demonstrates multi-agent planning, explicit capability routing, least-privilege tool permissions, failure recovery, safe re-routing, execution tracing, API design, automated testing, frontend observability, and iterative control-plane engineering. It also demonstrates a test-driven workflow: establish a normal baseline, inject a controlled failure, verify recovery, inject an authorization violation, verify the guardrail, then add operational telemetry around those behaviors.

Portfolio scope

Agent Orchestration Lab is a working local systems-engineering prototype, not a claim of operating a production autonomous-agent platform. The current portfolio environment uses deterministic simulated tools so failure, fallback, permission, timing, and recovery behavior can be reproduced without external API cost or provider drift. The orchestration logic, permission enforcement, API endpoints, run analytics, automated tests, and Mission Control interface are working software.
